# Pura

App di benessere per iOS/Android — Flutter + Supabase (Postgres, Auth, Storage, Edge Functions) + Gemini per consigli personalizzati generati sui dati reali dell'utente.

Progetto personale, non un esercizio: nasce come riscrittura seria di un prototipo React fatto su Lovable ([pura-wellness-flow.lovable.app](https://pura-wellness-flow.lovable.app)), usato solo come riferimento di prodotto — il codice qui è scritto da zero.

## Cosa funziona davvero

- **Autenticazione** — email/password via Supabase Auth
- **Routine mattutina** — checklist giornaliera sincronizzata, si azzera ogni giorno
- **Diversità vegetale settimanale** — traccia piante uniche mangiate in 7 giorni (indicatore di salute del microbioma)
- **Sonno** — registrazione manuale o import da Apple Salute (HealthKit)
- **Digiuno** — traccia primo/ultimo pasto, finestra di digiuno vs obiettivo
- **Skincare** — foto prodotti mattino/sera, salvate su Supabase Storage (bucket privato, RLS per cartella utente)
- **Suoni** — link Spotify/Apple Music/podcast del giorno
- **Lab** — inventario ingredienti dell'utente, matching automatico contro una libreria di ricette/tonici funzionali, diario di cosa è stato preparato
- **Scopri** — contenuti editoriali (sfide, protocolli stagionali)
- **Focus del giorno** — un consiglio personalizzato al giorno, generato da Gemini leggendo un digest aggregato dei dati recenti dell'utente (non i log grezzi — vedi sotto)
- **Impostazioni** — tema chiaro/scuro/sistema

**In lavorazione:** libreria "Pratiche" (categorie di abitudini da aggiungere alla propria routine — solo una categoria ha contenuto reale finora, le altre aspettano contenuto).

## Decisioni di architettura degne di nota

- **RLS ovunque.** Ogni tabella ha Row Level Security: un utente legge/scrive solo le proprie righe, anche se la chiave pubblica dell'app fosse esposta.
- **Nessun fallback locale silenzioso.** Le scritture (routine, piante, ecc.) vanno dirette su Supabase; se falliscono, l'interfaccia torna indietro e avvisa invece di fingere che sia andato tutto bene.
- Per le decisioni specifiche sulla parte AI (structured output, safety layer, observability, privacy), vedi la sezione **AI Architecture** sotto — in inglese, pensata per essere letta anche fuori da questo repo.

## AI Architecture

The "Focus del giorno" feature — a daily personalized suggestion generated by an LLM reading an aggregated digest of the user's recent data — is the most engineering-dense part of this project. Design choices below, in order of how the request actually flows.

**1. Server-side only, key never touches the client.**
The Flutter app never calls the LLM directly. It calls a Supabase Edge Function (`supabase/functions/focus-del-giorno`, Deno) with the user's JWT. The function re-derives identity from that JWT, queries Postgres *as that user* (so Row Level Security applies inside the function too, not just at the client), and only then calls the LLM. The API key lives in Supabase secrets — never in the repo, never in the app bundle.

**2. Context digest, not raw history.**
Sending months of raw event logs to an LLM on every request scales cost linearly and dilutes signal. The function aggregates on the fly (completion counts, unique-item counts over the last 7 days) into a compact digest before building the prompt.

**3. Structured output, validated server-side, no free-text parsing.**
The Gemini call uses `responseSchema` to force a JSON shape: `{ observation, evidence, recommendation, confidence, evidence_strength, sources, safety_category }`. The Edge Function validates every field's type and enum membership before returning anything — a malformed or missing field is an explicit `502` error, never a silently-accepted partial object. The Flutter client only renders typed fields; it does no text parsing.

**4. Independent safety layer — not just self-reported.**
The model's own `safety_category` (from the same call that generated the content) is treated as an untrusted signal, not a verdict — trusting a generator to grade its own output is a known failure mode. A second, independent pass re-classifies the `observation`+`recommendation` text alone, with a narrower prompt that has no view of the original digest, plus a small rule-based keyword check as a cheap backstop. The three signals combine conservatively (any one flagging `diagnosis_treatment` wins). Outcomes:
   - `diagnosis_treatment` → the recommendation is replaced with a message pointing to a professional, never shown as personal medical advice.
   - `medical_information` without concrete supporting evidence → replaced with a similar caveat (medical claims require grounding).
   - `concerning_signal` → an explicit "consider talking to a professional" line is appended.
   - `wellness_recommendation` → passes through unchanged.

   Every decision (categories + action taken, never the content) is logged to `safety_events` for later auditing of block/modify frequency.

**5. Observability, metadata-only.**
Every call writes to `llm_call_logs`: model, prompt version, latency, input/output token counts, an estimated cost, any error, and the final safety category — never prompt or suggestion text. A view (`llm_call_logs_summary_7d`) aggregates safety-flag rate, average latency, and average/total cost over the last 7 days, scoped by RLS (`security_invoker`).

**6. Native multimodal grounding for documents.**
If the user has uploaded a document (e.g. a nutritionist's report), the most recent one is attached to the Gemini request as `inline_data` (base64 PDF/image) — read natively by the model, no custom OCR/text-extraction step to maintain.

**7. Provider choice was a cost decision, not a default.**
Gemini Flash was chosen after estimating real cost at this app's actual usage pattern (a handful of requests/user/day) — not by defaulting to "the best-known model." `scripts/benchmark_providers.ts` is a standalone, reproducible comparison harness (not part of the production path) that runs the same 15 synthetic test cases — spanning plain wellness cases, grounded vs. ungrounded medical claims, and cases designed to pressure a model toward a diagnosis or flag a concerning signal — against both Gemini Flash and Mistral Small, checking schema compliance, expected-category match, latency, and cost. Run it with:
```
GEMINI_API_KEY=... MISTRAL_API_KEY=... deno run --allow-net --allow-write --allow-env scripts/benchmark_providers.ts
```
Results are written to `scripts/benchmark_results/` as CSV + Markdown, not committed as a single "final" verdict — they're meant to be regenerated as prompts/models change.

**8. Privacy is documented, not just implemented.**
[`PRIVACY_ARCHITECTURE.md`](PRIVACY_ARCHITECTURE.md) describes exactly what data reaches the LLM provider (and what explicitly doesn't), how RLS and private Storage buckets constrain every request, what the logs do and don't contain, and — honestly — what data-deletion functionality exists today versus what's still missing.

## Setup locale

1. [Flutter](https://docs.flutter.dev/get-started/install) installato e funzionante (`flutter doctor`)
2. Crea un progetto su [supabase.com](https://supabase.com), copia `lib/services/supabase_config.example.dart` in `lib/services/supabase_config.dart` con URL e chiave pubblica del tuo progetto (file escluso da git)
3. [Supabase CLI](https://supabase.com/docs/guides/cli) → `supabase link --project-ref <ref>` → `supabase db push` per applicare le migrazioni
4. Per la Edge Function: vedi `supabase/functions/focus-del-giorno/DEPLOY.md`
5. `flutter pub get && flutter run`
